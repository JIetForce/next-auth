## 2. Безопасность

### 2.1. 🔴 Весь rate limiting обходится одним HTTP-запросом

`toNextJsHandler(auth)` в [src/app/api/auth/[...all]/route.ts:6](src/app/api/auth/[...all]/route.ts:6)
монтирует **весь** REST API Better Auth: `POST /api/auth/sign-in/email`, `/sign-up/email`,
`/forget-password`, `/reset-password`, `/send-verification-email`, `/sign-in/social`.

Аккуратно написанные лимиты живут только в Server Actions:

- [login/actions.ts:53-59](src/app/(auth)/login/actions.ts:53) — 5 попыток на email / 15 мин
- [register/actions.ts:46-52](src/app/(auth)/register/actions.ts:46) — 3 на email / час
- [reset-password/actions.ts:30-33](src/app/(auth)/reset-password/actions.ts:30)
- [verify-email/actions.ts:27-33](src/app/(auth)/verify-email/actions.ts:27)

Клиент, который бьёт напрямую в `/api/auth/sign-in/email`, не проходит ни одну из этих проверок.
Брутфорс пароля упирается только во встроенный лимитер Better Auth, а он в
[src/auth.ts](src/auth.ts) не сконфигурирован вообще — значит действуют дефолты: включён
**только в production**, 100 запросов / 60 с на IP суммарно по всем путям, хранилище — память
процесса. Для подбора пароля 100 попыток в минуту — это не лимит.

**Фикс:**

```ts
// src/auth.ts
rateLimit: {
  enabled: true,                 // включить и в dev, иначе E2E ничего не проверит
  storage: "database",           // требует модель RateLimit в prisma/schema.prisma
  window: 60,
  max: 100,
  customRules: {
    "/sign-in/email":  { window: 900, max: 10 },
    "/sign-up/email":  { window: 3600, max: 5 },
    "/forget-password":{ window: 3600, max: 5 },
    "/reset-password": { window: 3600, max: 10 },
  },
},
```

`storage: "database"` требует добавить модель `RateLimit` в схему Prisma — сейчас её там нет
(получить каноническое определение: `npx @better-auth/cli generate`).

### 2.2. 🔴 Собственный лимитер бесполезен на serverless и течёт памятью

[src/lib/auth/rate-limit.ts:9](src/lib/auth/rate-limit.ts:9) — `const buckets = new Map()` на уровне
модуля. Два независимых дефекта:

1. **Per-instance.** На Vercel каждый инстанс лямбды получает свою `Map`. При 10 тёплых инстансах
   лимит «5 попыток» превращается в 50. При скейлинге под нагрузкой — в произвольное число.
2. **Ключи не вычищаются.** Просроченный бакет перезаписывается только когда по тому же ключу
   придёт новый запрос ([rate-limit.ts:23-26](src/lib/auth/rate-limit.ts:23)). Ключ содержит
   произвольный email атакующего (`signin:email:${email}`), удаления нет нигде — на долгоживущем
   процессе (`npm start`, контейнер) `Map` растёт неограниченно. Это дешёвый DoS по памяти.

**Фикс:** убрать модуль целиком и передать лимиты Better Auth (см. 2.1) либо, если нужен внешний
стор, взять `@upstash/ratelimit` + Upstash Redis. Держать два независимых лимитера — гарантия
расхождения.

### 2.3. 🟠 IP определяется неверно за прокси

Во всех четырёх экшенах ([login:49-51](src/app/(auth)/login/actions.ts:49),
[register:42-44](src/app/(auth)/register/actions.ts:42),
[reset-password:28-29](src/app/(auth)/reset-password/actions.ts:28),
[verify-email:23-25](src/app/(auth)/verify-email/actions.ts:23)):

```ts
(await headers()).get("x-forwarded-for")?.split(",").pop()?.trim() ?? "unknown"
```

`.pop()` берёт **последний** элемент цепочки, то есть ближайший прокси, а не клиента. Логика
«последний = недоверенный клиент не мог его подделать» разумна, но за фронтендом Vercel это даёт
один и тот же адрес для всех, и per-IP бакет схлопывается в один глобальный.

**Фикс:** `@vercel/functions` уже в зависимостях и экспортирует `ipAddress()`:

```ts
import { ipAddress } from "@vercel/functions";
const ip = ipAddress(request) ?? "unknown";
```

Либо `advanced.ipAddress.ipAddressHeaders` в Better Auth, если лимиты переезжают туда.

### 2.4. 🟠 `resetPasswordAction` не ограничен вообще

[reset-password/actions.ts:52-73](src/app/(auth)/reset-password/actions.ts:52) — единственный
экшен без `consumeRateLimit`. Токены Better Auth высокоэнтропийны, так что практический перебор
маловероятен, но это дыра в остальном последовательной модели, и такой же незащищённый
`POST /api/auth/reset-password` доступен напрямую.

### 2.5. 🟠 Нет заголовков безопасности

[next.config.ts](next.config.ts) не определяет `headers()`. Приложение с формами логина
и паролями отдаётся без `Content-Security-Policy`, `Strict-Transport-Security`,
`X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options` / `frame-ancestors`.

Отсутствие `frame-ancestors` означает, что `/login` можно поместить в iframe — база для
clickjacking. Минимум:

```ts
async headers() {
  return [{
    source: "/:path*",
    headers: [
      { key: "X-Content-Type-Options", value: "nosniff" },
      { key: "Referrer-Policy", value: "strict-origin-when-cross-origin" },
      { key: "X-Frame-Options", value: "DENY" },
      { key: "Strict-Transport-Security", value: "max-age=63072000; includeSubDomains; preload" },
      { key: "Permissions-Policy", value: "camera=(), microphone=(), geolocation=()" },
    ],
  }];
}
```

CSP отдельной задачей — с Tailwind v4 и next-themes потребуется nonce для инлайн-скрипта темы.

### 2.6. 🟠 `BETTER_AUTH_URL` — мина при деплое

[better-auth/dist/utils/url.mjs:71](node_modules/better-auth/dist/utils/url.mjs:71) читает
`BETTER_AUTH_URL` **раньше**, чем что-либо выводит из запроса. В `.env.example:5` и в
README указано `BETTER_AUTH_URL="http://localhost:3000"` без раздела «а в production — вот так».
Скопировав `.env.example` в переменные Vercel, вы получите `redirect_uri=http://localhost:3000/...`
в каждом OAuth-запросе и неработающий вход в проде.

Плюс `trustedOrigins` в [src/auth.ts](src/auth.ts) не задан — единственная защита от CSRF на
эндпоинтах Better Auth выводится из baseURL, то есть из той же переменной.

**Фикс:** документировать production-значение, а в конфиге вывести baseURL из
`VERCEL_PROJECT_PRODUCTION_URL` с фолбэком, и явно задать `trustedOrigins`.

### 2.7. 🟡 Google-провайдер регистрируется всегда, даже без ключей

[src/auth.ts:60-65](src/auth.ts:60) — `clientId: process.env.GOOGLE_CLIENT_ID ?? ""`. Проверка
`isGoogleAuthConfigured()` защищает только Server Action
([login/actions.ts:12](src/app/(auth)/login/actions.ts:12)). Прямой
`POST /api/auth/sign-in/social {"provider":"google"}` при пустых ключах уйдёт в Google с пустым
`client_id` вместо понятной ошибки. Регистрировать провайдер условно.

### 2.8. 🟡 Парольная политика ниже актуальных рекомендаций

[src/auth.ts:15](src/auth.ts:15) — `minPasswordLength: 6`; правило «буква + цифра» продублировано
в [validation.ts:10](src/lib/auth/validation.ts:10) и [schemas.ts:16-28](src/lib/auth/schemas.ts:16).

NIST SP 800-63B: минимум 8 символов, а композиционные правила («обязательно цифра») **прямо
не рекомендуются** — они предсказуемо дают `password1`. Полезнее: минимум 8–12 без композиционных
правил + проверка по утечкам через k-anonymity API Have I Been Pwned в
`emailAndPassword.password.hash`-соседнем хуке или в самом экшене.

### 2.9. 🟡 Данные в БД растут без границ

[prisma/schema.prisma:28-42](prisma/schema.prisma:28) (`session`) и
[66-76](prisma/schema.prisma:66) (`verification`): нет индекса по `expiresAt` и нет ничего, что
удаляло бы просроченные строки. За год таблица `verification` наберёт по строке на каждое
письмо. Нужен индекс + cron (Vercel Cron / `pg_cron`) с `DELETE WHERE "expiresAt" < now()`.

### 2.10. 🟡 Личный IP в трекаемом конфиге

[next.config.ts:5](next.config.ts:5) — `allowedDevOrigins: ["192.168.31.145"]`. Адрес домашней
сети в репозитории, и E2E-тест
[login.spec.ts:13](e2e/login.spec.ts:13) на него завязан. Вынести в переменную окружения.

**Проверено и чисто:** в истории git нет закоммиченных `.env*` (кроме `.env.example`), нет
Google client secret'ов, приватных ключей и токенов. `git log --all -S` по характерным префиксам
ничего не находит. Формулировка в `auth-architecture.md:142` о «previously disclosed Google client
secret» относится к утечке вне репозитория.

## 3. Архитектурные проблемы

### 3.1. 🔴 Всё приложение рендерится динамически — включая лендинг

Вывод `npm run build`:

```
┌ ƒ /
├ ○ /_not-found
├ ƒ /api/auth/[...all]
├ ƒ /features
├ ƒ /pricing
├ ƒ /profile
...
```

**Ни одна** страница, кроме `_not-found`, не пререндерится. Причина: `Header` рендерится в обоих
layout'ах ([(main)/layout.tsx:8](src/app/(main)/layout.tsx:8),
[(auth)/layout.tsx:9](src/app/(auth)/layout.tsx:9)) → `HeaderAccount` → `getCurrentViewer()` →
`headers()`. Одно чтение заголовков делает динамическим всё дерево.

То есть маркетинговый лендинг с статичным контентом ходит в Postgres за сессией на каждый заход
анонимного посетителя. Это худший из возможных TTFB для страницы, которую можно было бы отдавать
с CDN.

**Фикс есть, и он дешёвый.** Suspense-граница уже стоит там, где надо
([header.tsx:49-53](src/components/header.tsx:49)) — ровно та форма, которую требует Cache
Components в Next 16. Включить `cacheComponents: true` в `next.config.ts`: статическая оболочка
уходит на CDN, аккаунт-слот стримится. См.
`node_modules/next/dist/docs/01-app/02-guides/authentication-with-cache-components.md` и
`migrating-to-cache-components.md` — там же описан `export const instant = false` как способ
мигрировать маршрут за маршрутом, не ломая всё разом.

### 3.2. 🟠 Запрос в БД за сессией на каждый HTTP-запрос

[src/auth.ts](src/auth.ts) не задаёт `session.cookieCache`. Дефолт — `enabled: false`
(подтверждено в `@better-auth/core/dist/types/init-options.d.mts:952-960`), то есть каждый вызов
`auth.api.getSession` — это SELECT в Postgres. React `cache()` в
[session.ts:12](src/lib/auth/session.ts:12) дедуплицирует внутри одного рендера, но не между
запросами.

```ts
session: {
  cookieCache: { enabled: true, maxAge: 300 },
},
```

Пять минут кэша в подписанной куке убирают round-trip к БД с горячего пути. Отзыв сессии тогда
вступает в силу с задержкой до `maxAge` — это осознанный размен, который надо записать в
`auth-architecture.md`.

### 3.3. 🟠 `Viewer` без `id` — тупик для любой авторизации

[src/lib/auth/types.ts:1-5](src/lib/auth/types.ts:1) — `{ name, email, image }`.
[session.ts:18-22](src/lib/auth/session.ts:18) явно проецирует только эти три поля.

Аллоулист сам по себе правильный. Но `id` в нём нет, а без `id` невозможна ни одна проверка
владения (`post.authorId === viewer.id`) — как только появится первая пользовательская сущность,
придётся либо расширять DTO, либо делать второй запрос к БД, либо (худший исход) сравнивать по
email. `emailVerified` тоже не проброшен, хотя на нём завязана вся логика верификации.

`id` — не секрет: это внутренний идентификатор, он не утечёт «наружу» сильнее, чем email, который
уже в DTO. Добавить `id` и `emailVerified` сейчас, пока потребителей два.

### 3.4. 🟠 Две параллельные системы валидации, уже разошедшиеся

- Клиент: zod-схемы в [src/lib/auth/schemas.ts](src/lib/auth/schemas.ts) через `zodResolver`.
- Сервер: рукописный regex `isValidEmail` в
  [register/actions.ts:17-19](src/app/(auth)/register/actions.ts:17) + `isValidPassword` в
  [validation.ts:9-11](src/lib/auth/validation.ts:9).

Server Actions **не используют zod вообще**. Одно и то же правило про пароль записано в трёх
местах: `schemas.ts:16-28`, `schemas.ts:52-65`, `validation.ts:10`. Правило про совпадение
паролей — в `schemas.ts:31` и в `register/actions.ts:38` и в `reset-password/actions.ts:60`.

Схемы при этом уже неполны относительно сервера: `registerSchema` не приводит email к нижнему
регистру, а экшен приводит ([register/actions.ts:27-29](src/app/(auth)/register/actions.ts:27)).

**Фикс:** одна схема, `safeParse` на сервере, `zodResolver` на клиенте, `validation.ts` удалить.
Это ровно то, для чего zod 4 и `@hookform/resolvers` уже стоят в зависимостях.

### 3.5. 🟠 Нет ни одного файлового соглашения App Router для ошибок

Во всём `src/app` отсутствуют: `error.tsx`, `global-error.tsx`, `not-found.tsx`, `loading.tsx`,
`middleware.ts`, `robots.ts`, `sitemap.ts`.

Практическое следствие: [session.ts:15](src/lib/auth/session.ts:15) намеренно пропускает ошибки
Better Auth наверх (это задокументировано и правильно) — но ловить их некому. Падение Postgres
на проде даёт пользователю дефолтную страницу Next вместо брендированной, и ничего не логируется.

### 3.6. 🟡 Источник контента расщеплён

[src/lib/content.ts:25-43](src/lib/content.ts:25) содержит три FAQ. Лендинг рендерит их из
`sharedFaqs`, а затем **дописывает ещё два инлайном**

То есть два FAQ существуют лишь на одной странице и не редактируются вместе с остальными.

## 8. Что сделано хорошо

Чтобы отчёт был честным — вот что не надо трогать:

- **Разделение Server/Client образцовое.** `Viewer`-DTO вместо сырой сессии, `server-only` на
  каждом серверном модуле, клиентские компоненты — листья.
- **Единообразные ответы против энумерации.** [login/actions.ts:64-69](src/app/(auth)/login/actions.ts:64),
  [reset-password/actions.ts:13-15](src/app/(auth)/reset-password/actions.ts:13),
  [verify-email/actions.ts:11-13](src/app/(auth)/verify-email/actions.ts:11) — один ответ на все
  исходы, и письма отправляются без `await` именно чтобы тайминг не выдавал существование адреса.
  Это редко делают правильно.
- **Комментарии объясняют «почему».** [db.ts:21-24](src/lib/db.ts:21) про `attachDatabasePool`,
  [auth.ts:73](src/auth.ts:73) про порядок `nextCookies()`,
  [playwright.config.ts:9-22](playwright.config.ts:9) про то, почему DB URL нельзя пробрасывать
  в дочерний процесс. Это лучше среднего по индустрии.
- **Защита тестовой БД.** [global-setup.ts:21-25](e2e/global-setup.ts:21) отказывается делать
  `migrate reset`, если в имени БД нет `apptest`.
- **Схема Prisma точно соответствует Better Auth 1.7**, включая нетривиальное поле `issuer` и
  уникальный индекс `(issuer, accountId)`.
- **Roster-тулинг здоров:** 33/33 тестов, 35 профилей в синхроне, валидатор и доктор зелёные.
- **Секретов в истории git нет.**
