# Better Auth Migration and Email/Password Registration Design

## Status

This design replaces Auth.js (`next-auth@5.0.0-beta.32`) with Better Auth, introduces the project's first database, and adds email/password registration, email verification, and password recovery alongside the existing Google sign-in.

It supersedes the auth stack chosen in `2026-08-30-google-auth-design.md` and `2026-08-30-auth-profile-foundation-design.md`. Those remain decision records. After implementation, `docs/auth-architecture.md` is rewritten and stays the canonical application-auth reference.

The Google client secret disclosed during earlier debugging must be rotated before any real-provider smoke test. No credential value may be copied into tracked files, tests, reports, logs, or conversation.

## Why the stack changes

The migration is not driven by the feature request alone. Auth.js is no longer actively developed:

- Auth.js is now maintained by the Better Auth team, security patches and urgent issues only. Its own announcement states: "we strongly recommend new projects to start with Better Auth unless there are some very specific feature gaps."
- On `next-auth` v5 leaving beta, the maintainer states: "We don't have any immediate plans for v5."

This repository is pinned to `next-auth@5.0.0-beta.32`, a beta with no stable release path. Adding password authentication on that foundation would build new security-sensitive surface on a dead-ended dependency.

Verified compatibility at design time: `better-auth@1.7.2` declares peer ranges `next: ^14 || ^15 || ^16` and `react: ^18 || ^19`, satisfied by the pinned `next@16.3.3` and `react@19.2.8`. The project sets `reactCompiler: true` and does not enable `cacheComponents`, so the Cache Components authentication rules do not apply.

## Goals

- Replace Auth.js with Better Auth as the single authentication boundary.
- Add email/password registration with mandatory email verification before first sign-in.
- Add self-service password recovery by emailed single-use token.
- Keep Google sign-in working and link a Google identity to an existing password account with the same verified address.
- Introduce Postgres (Supabase) with Prisma as the project's persistence layer, sized for future non-auth data.
- Preserve the existing server-first session contract: the `Viewer` DTO, the DAL surface, redirect pinning, and per-boundary authorization checks.
- Gain central session revocation, which the JWT-only architecture explicitly could not provide.
- Deliver an email transport abstraction that swaps providers without touching auth or UI code.
- Test every new flow end to end without real credentials, real mailboxes, or production test hooks.

## Non-goals

- Migrating existing user records. There is no database today, so there is no data to migrate.
- Two-factor authentication, passkeys, magic links, organizations, or roles and permissions.
- Additional OAuth providers beyond the existing Google.
- Supabase Auth, Supabase RLS, Supabase Storage, or Supabase Realtime. Supabase is a Postgres host only.
- A global `SessionProvider`, `useSession()`, focus polling, or cross-tab session synchronization.
- `proxy.ts` or middleware as an authorization boundary.
- Editable profile fields, avatar upload, or account deletion.
- User-controlled callback URLs, return-to paths, provider IDs, or logout destinations.
- Changing existing `/features` or `/pricing` behavior.
- Adding application architecture to `AGENTS.md`.

## Fixed decisions

- Auth library: Better Auth `1.7.2`, pinned exactly.
- ORM: Prisma `7.10.0`, pinned exactly. The `prisma` CLI package's `latest` dist-tag has advanced to `8.0.0-rc.12` (a release candidate); `7.10.0` is the last stable 7.x release and is installable via `npm install prisma@7.10.0 @prisma/client@7.10.0 @prisma/adapter-pg@7.10.0`. Do not install `prisma@latest`.
- Database: Supabase Postgres, accessed through the pooled connection string.
- Email transport: Mailpit as the sole mail server (local, E2E, and deployment). No external email provider is configured. The transport abstraction remains so a provider can be added later by swapping one module.
- Configuration boundary stays at `src/auth.ts`, matching the existing documented file ownership.
- Auth route moves from `src/app/api/auth/[...nextauth]/route.ts` to `src/app/api/auth/[...all]/route.ts`.
- Sessions are database-backed. The JWT cookie strategy is removed.
- Email verification is mandatory: `requireEmailVerification: true`, `autoSignIn: false`.
- Password reset revokes all other sessions.
- Account linking is enabled with `google` as the only trusted provider.
- Successful sign-in destination: `/`. Anonymous protected destination: `/login`. Logout destination: `/`. Unchanged from the current contract.
- The auth schema is generated by the Better Auth CLI, never hand-written.

## Rejected alternatives

Recorded because each was considered seriously and the reasoning should survive.

**Auth.js with a Credentials provider.** Would avoid the migration, but requires hand-writing registration, verification, reset, token lifecycle, and enumeration resistance on a dependency that is in security-only maintenance with no stable release path.

**Supabase Auth for both storage and authentication.** Attractive for its single-platform simplicity, and rejected after measuring the actual difference. The page count, Server Action count, and E2E rewrite are identical either way. Supabase's built-in SMTP is capped at two messages per hour and is documented as non-production, so an external provider would still be needed; the hoped-for email advantage does not exist. What remains is a trade of portability for vendor coupling on the single hardest component to migrate later, plus the `auth.users` trigger-and-`profiles` pattern, which is not simpler than a generated schema, and a mandatory `getUser()` network round-trip at every authorization boundary because `getSession()` is not trustworthy server-side.

**Drizzle ORM.** Leads Prisma on weekly npm downloads, but the `latest` dist-tag is `0.45.2`, published 2026-03-27 and unchanged since, while v1 sits at `1.0.0-rc.5`. Starting a new foundation there means committing to a frozen branch and a guaranteed later migration with breaking changes. Prisma `7.10.0` is a released, semver-respecting major on a regular cadence, and its historical bundle-size disadvantage was resolved in Prisma 7.

**Neon instead of Supabase.** Neon reactivates automatically in hundreds of milliseconds after arbitrary idle time, which suits a portfolio project better than Supabase's manual restore. Supabase was retained by explicit decision for its storage and realtime headroom; see the accepted risk below.

## Accepted risks

These are known, decided, and must not be re-litigated during implementation. They are documented so a future reader does not mistake them for oversights.

**Supabase inactivity pause.** Supabase free-tier projects pause after seven days of inactivity and require a manual restore from the dashboard. The obvious mitigation does not work: GitHub disables scheduled workflows after 60 days without repository activity, and only commits reset that timer, so a keep-alive cron dies before the project it protects. No workflow is added. The operational procedure is instead explicit: while the repository is under active development the pause will not trigger; once development stops, the project must be restored manually before the application is shared, or the database moved to a host that wakes on demand.

**Email deliverability is explicitly not a requirement.** No custom domain will be purchased. Mail is sent through a free SMTP provider (Brevo's free tier, 300/day, needs only a verified sender address, not a domain) or any authenticated SMTP account. Messages will frequently land in spam because the sender is unauthenticated; this is accepted and must not be designed around. Locally and in E2E the transport points at Mailpit instead. `src/lib/email/client.ts` is the only module that knows which transport is in use.

**Better Auth minor releases can break.** Version 1.7.0 shipped more than fifteen breaking changes and required schema regeneration. The project does not follow strict semver on minors and releases roughly weekly. The version is pinned exactly, upgrades are deliberate and reviewed, and no upgrade is performed as a side effect of unrelated work.

## Database and Prisma configuration

The Better Auth CLI generates four models into `prisma/schema.prisma`: `User`, `Session`, `Account`, and `Verification`. `Verification` backs both email confirmation and password reset; no separate token model is introduced.

```bash
npx auth@latest generate --adapter prisma --dialect postgresql
npx prisma migrate dev --name add-better-auth
npx prisma generate
```

The CLI writes the schema but does not run migrations. In Prisma 7 `migrate dev` does not regenerate the client into a custom output directory either, so `prisma generate` runs after every schema change.

Prisma 7 specifics that differ from earlier majors and must not be copied from older examples:

- The generator is `prisma-client`, not `prisma-client-js`, and `output` is required.
- The project is ESM (`"type": "module"`), so the generator sets `moduleFormat = "esm"`.
- The datasource URL is configured in `prisma.config.ts`, not inline in the schema.
- Connections use the `@prisma/adapter-pg` driver adapter.
- The CLI package is `auth` (`npx auth@latest`), currently `1.7.2`. The older `@better-auth/cli` package is
  stale at `1.4.21` and must not be used.

`src/lib/db.ts` owns a single `PrismaClient` instance behind a `globalThis` guard so hot reload does not exhaust connections. It is `server-only`. No route, component, or action constructs its own client.

## Auth configuration boundary

`src/auth.ts` exports `auth` and remains the only file that configures providers, sessions, or auth behavior.

Configuration covers:

- `database: prismaAdapter(prisma, { provider: "postgresql" })`
- `emailAndPassword`: `enabled`, `requireEmailVerification: true`, `autoSignIn: false`, `minPasswordLength: 12`, `maxPasswordLength: 128`, `sendResetPassword`, `resetPasswordTokenExpiresIn: 3600`, `revokeSessionsOnPasswordReset: true`
- `emailVerification`: `sendOnSignUp: true`, `sendVerificationEmail`
- `socialProviders.google`
- `account.accountLinking`: `enabled: true`, `trustedProviders: ["google"]`
- Built-in rate limiting, enabled for auth endpoints

`customSyntheticUser` is omitted. Better Auth's enumeration resistance is built-in: when `requireEmailVerification: true` or `autoSignIn: false`, a sign-up with an already-registered email returns a synthetic `200` with no session token, indistinguishable from a real sign-up response. `customSyntheticUser` is only needed when plugins add custom fields to the user table so the synthetic response matches a real one; with this design's plugin set (`nextCookies()` only), the default synthetic response is already indistinguishable.

Better Auth's built-in rate limiter is **disabled by default in development** and enabled in production at 100
requests per 60 seconds, with stricter built-in rules on sensitive endpoints (email sign-in is capped at 3
requests per 10 seconds). It covers client-initiated HTTP requests to the auth handler (`/api/auth/*`), but
**does not cover server-side `auth.api.*` calls** from Server Actions — the library treats in-process calls as trusted. Since this design's registration, sign-in, resend, and reset Server Actions call `auth.api.signUpEmail` / `auth.api.signInEmail` / `auth.api.sendVerificationEmail` / `auth.api.requestPasswordReset` directly, those paths are not protected by the built-in limiter. Application-level rate limiting is therefore required in each Server Action (see § Security properties).

Password hashing uses the library default. A custom `password.hash` / `password.verify` pair is not introduced; replacing a maintained default with bespoke crypto adds risk without benefit.

Both `sendVerificationEmail` and `sendResetPassword` dispatch without awaiting the transport, per Better Auth guidance, so response time does not leak whether an address exists.

## Session boundary and Viewer DTO

`src/lib/auth/types.ts` is unchanged. `Viewer` stays `{ name, email, image }`.

`src/lib/auth/session.ts` keeps both exports and both signatures:

- `getCurrentViewer(): Promise<Viewer | null>`, still a module-level React `cache()`.
- `requireCurrentViewer(): Promise<Viewer>`, still redirecting to `/login`.

Only the internals change: `auth()` becomes `auth.api.getSession({ headers: await headers() })`. The returned object is still constructed field by field and never spread.

Because the DAL surface is preserved, `src/app/(main)/profile/page.tsx`, `src/components/header-account.tsx`, and every existing authorization check require no modification. This is the primary reason the migration is tractable.

Unexpected library or runtime errors still propagate to the Next.js error boundary rather than degrading silently to anonymous state.

## Email infrastructure

`src/lib/email/client.ts` exposes one function: `sendEmail({ to, subject, text, html })`. It is `server-only`.

It selects a transport from environment configuration. Today the sole transport is SMTP to a Mailpit instance, used in local development, E2E, and deployment. Mailpit accepts mail for any address, stores it, and exposes a web UI (port `8025`) and REST API. No external email provider is configured. Swapping to a real provider later (Resend, Brevo, or any SMTP/HTTP API) replaces this module only. No caller changes.

Templates are plain functions returning subject and body. Every link is built from a server-owned base URL; no link target derives from request input.

When email configuration is absent the module fails loudly at send time and the calling flow reports a generic failure. It never silently drops a verification or reset message.

## Registration and verification flow

1. `/register` renders a Server Component form posting to a Server Action.
2. The action validates with Zod before calling the library: a parseable email address, a password of at least 12 characters containing at least one letter and one digit, and a matching confirmation field. The 12-character minimum is asserted in both places, so a direct API call cannot bypass the form rule.
3. It calls `auth.api.signUpEmail`.
4. `sendOnSignUp` dispatches the verification message.
5. Because `autoSignIn` is `false` and `requireEmailVerification` is `true`, no session is created.
6. The browser lands on `/verify-email`, which instructs the user to check the Mailpit web UI (port `8025`) for the verification message and offers a rate-limited resend.
7. The emailed link hits the Better Auth handler, marks the address verified, and redirects to `/login`.

Registration responses are uniform whether or not the address already exists. Better Auth's built-in enumeration resistance returns a synthetic `200` with no session token when the email is already registered (active because `requireEmailVerification: true` and `autoSignIn: false`), and the UI never distinguishes the two cases.

## Password reset flow

1. `/reset-password` accepts an address and always renders the same confirmation.
2. `sendResetPassword` dispatches a single-use token valid for one hour.
3. `/reset-password/[token]` validates the token server-side before rendering the form.
4. On success the password is replaced, all other sessions are revoked, and the user is sent to `/login`.

An invalid, expired, or already-used token renders a generic failure with a link to request a new one. It never reveals whether the token existed.

## Account linking

`accountLinking.enabled` with `trustedProviders: ["google"]` links a Google identity to an existing user with the same address.

Better Auth's `requireLocalEmailVerified` defaults to `true` (added in v1.6.11 to fix a pre-account-hijacking vulnerability, GHSA-g38m-r43w-p2q7). It is marked `@deprecated` in the type definitions and will become unconditional in the next minor release; the design keeps the explicit `true` for now and does not rely on the default. The consequence must be handled in the UI: a user who registered with a password but has not confirmed their address, then tries Google with that address, is refused with `account not linked`.

This default is correct, because linking to an unverified local account would let an attacker pre-register a victim's address and capture the later OAuth identity. The design keeps it and instead makes the refusal legible: `/login` renders an explicit message telling the user to confirm their address first, with a resend control.

## Redirect and state matrix

| State or action                                            | Result                                        |
| ---------------------------------------------------------- | --------------------------------------------- |
| Anonymous `GET /`                                          | `200`; Header shows Sign in                   |
| Authenticated `GET /`                                      | `200`; Header shows the account menu          |
| Anonymous `GET /profile`                                   | Redirect to `/login`                          |
| Authenticated `GET /login`, `/register`, `/reset-password` | Redirect to `/`                               |
| Registration submitted                                     | Redirect to `/verify-email`; no session       |
| Sign-in before verification                                | Refused; prompt to verify with resend control |
| Valid verification link                                    | Address marked verified; redirect to `/login` |
| Valid reset link                                           | Render new-password form                      |
| Invalid or expired reset link                              | Generic failure and a request-again link      |
| Successful sign-in, either method                          | Redirect to `/`                               |
| Google sign-in matching an unverified local account        | Refused; verify-first message                 |
| Authenticated logout submit                                | Session row deleted; redirect to `/`          |

Every destination remains a fixed compile-time path. No query parameter, form field, or cookie selects a destination.

## Environment separation

```text
DATABASE_URL              # Supabase pooled connection
DIRECT_URL                # Supabase direct connection, for migrations
BETTER_AUTH_SECRET        # session and token encryption
BETTER_AUTH_URL           # server-owned base URL for emailed links
GOOGLE_CLIENT_ID
GOOGLE_CLIENT_SECRET
SMTP_HOST / SMTP_PORT / EMAIL_FROM        # Mailpit: localhost:1025
SMTP_USER / SMTP_PASSWORD                 # optional; unset for Mailpit, set for any authenticated SMTP
```

`AUTH_GOOGLE_ID` and `AUTH_GOOGLE_SECRET` are renamed. `AUTH_SECRET` may be reused as `BETTER_AUTH_SECRET`, but existing sessions are invalidated regardless, because the session model itself changes.

`src/lib/auth/environment.ts` keeps the split-readiness idea: session reads require the secret and the database; starting Google sign-in additionally requires the Google pair; registration and recovery additionally require SMTP configuration. Each surface degrades independently instead of taking down the whole page.

No variable is prefixed `NEXT_PUBLIC_`. No value is printed or written to a tracked file.

## E2E strategy

The current seam, `e2e/helpers/auth-session.ts`, forges an Auth.js JWE cookie with `next-auth/jwt`. That API disappears with the dependency, so the helper is replaced rather than adapted. The existing `e2e/auth-session.spec.ts` and `e2e/login.spec.ts` assert behavior rather than session internals, so they are adapted at the seam rather than rewritten.

The replacement uses Better Auth's first-party `testUtils()` plugin (`better-auth/plugins`), which exposes `test.getCookies({ userId, domain })` returning Playwright-shaped cookie objects (`name: "better-auth.session_token"`, `httpOnly`, `sameSite`, etc.) ready for `context.addCookies()`. Internally it calls `ctx.internalAdapter.createSession(userId)` and signs the cookie with `BETTER_AUTH_SECRET` — a real database-backed session, not a forged token. Companion helpers cover the remaining seeding needs, in this order: `test.createUser(overrides)` builds an
in-memory user object and does **not** write to the database; `test.saveUser(user)` persists it;
`test.deleteUser(user.id)` cleans up. Calling `getCookies()` for a user that was never saved yields a session
pointing at a non-existent row. The `testUtils()` plugin lives in a **test-only auth instance** in `e2e/helpers/auth.test.ts`, not in `src/auth.ts`; conditional spreading into the production config breaks TypeScript inference of `ctx.test` and is avoided. The helper stays confined to `e2e/**` and must never be imported from `src/**`.

The disposable test database is a Docker Postgres container (`postgres:17`) started before the test run, exposed on a non-conflicting port (e.g. 5433), and reset between runs with `npx prisma migrate reset --force` in a Playwright `globalSetup`. This avoids the Supabase free-tier 7-day inactivity pause (see § Accepted risks) and gives fully disposable, no-shared-state isolation. `playwright.config.ts` passes the test database URL (`DATABASE_URL`), `DIRECT_URL`, `BETTER_AUTH_SECRET`, and SMTP env (`SMTP_HOST=localhost`, `SMTP_PORT=1025`) to the child server alongside the existing auth variables.

New specs:

- registration through verification to first successful sign-in;
- sign-in refused before verification;
- password reset, including that the old password stops working;
- reset token rejected when reused or expired;
- Google linking refused against an unverified local account;
- existing anonymous, authenticated, profile, redirect, and logout contracts, still green.

Mailpit is the mail sink for local and E2E runs. Its REST API listens on port `8025`: `GET /api/v1/messages` lists messages, `GET /api/v1/message/{id}` fetches a full message body, `DELETE /api/v1/messages` clears the mailbox. A Playwright helper fetches the message whose `To` matches the test user, extracts the verification or reset link from the body, and calls `DELETE /api/v1/messages` in `globalSetup` or `beforeEach` to reset state. No test sends real mail, uses real credentials, or persists authenticated `storageState`.

## Security properties

- Passwords are stored only as hashes produced by the library default.
- Verification and reset tokens are single-use, expiring, and validated server-side before any form renders.
- Registration and recovery responses are uniform, so neither confirms whether an address is registered.
- Email dispatch is not awaited, so response timing does not leak account existence.
- Reset revokes every other session, so a recovered account does not leave an attacker signed in.
- Sessions live in the database, so revocation is now immediate and central. This closes the limitation the previous architecture documented as unsolvable.
- Rate limiting covers sign-in, registration, resend, and reset request. Better Auth's built-in limiter protects client-initiated HTTP requests to `/api/auth/*`; Server Actions that call `auth.api.*` directly are not covered by it and require application-level rate limiting (in-memory or database-backed counter keyed by email and IP, with a configurable window).
- Account linking requires a verified local address, preventing pre-registration capture of a victim's address.
- The `Viewer` allowlist still bounds what crosses the server/client boundary.
- Destinations remain server-owned constants, so no open-redirect surface is introduced.
- Server Actions keep framework origin checks, with explicit authorization inside each action.
- `.gitignore` gains `/src/generated/` so the generated Prisma client is never committed and no build artifact carries connection details into the repository.

## Documentation architecture

`docs/auth-architecture.md` is rewritten in the same change, not afterwards. Four invariants are replaced:

| Current                                               | Replacement                                         |
| ----------------------------------------------------- | --------------------------------------------------- |
| Google OAuth is the only sign-in provider             | Google and email/password, with linking             |
| Encrypted JWT cookie sessions and no database adapter | Database-backed sessions via Prisma                 |
| Do not introduce a Credentials provider               | Withdrawn; the prohibition targeted a test backdoor |
| No central session revocation                         | Resolved; revocation is available                   |

Preserved unchanged: the `Viewer` projection rule, redirect pinning, the rule that every protected boundary checks itself, POST-backed logout, and the prohibitions on `SessionProvider`, `useSession()`, client-only authorization, and test auth routes.

`README.md` gains database and mail setup steps, and records the Supabase pause procedure from the accepted risks above.

## Staged delivery

Each stage is a full cycle through `developer`, then `verifier`, then the three reviewers in parallel, per `AGENTS.md`.

1. Database, Prisma, Supabase connection, generated schema and first migration.
2. Better Auth replaces Auth.js. Google sign-in works on the new stack. DAL exports unchanged. E2E seam replaced and existing specs green.
3. SMTP transport, templates, Mailpit wiring.
4. Registration, email verification, and email/password sign-in.
5. Password recovery.
6. Account linking, `/login` messaging, documentation rewrite.

Stage 2 is the risk concentration: it is the only stage where existing behavior can regress. It ships with no new user-facing features so that a failure there is unambiguous.

## Acceptance criteria

- `next-auth` is absent from `package.json` and from `src/**`.
- A new visitor registers, receives a verification message, confirms, and signs in.
- Sign-in before confirmation is refused with an actionable message and a working resend.
- Reset replaces the password, invalidates the old one, and revokes other sessions.
- A reset token cannot be reused and expires after one hour.
- Google sign-in still succeeds and links to a verified account with the same address.
- Google sign-in against an unverified local account is refused with a legible explanation.
- `/profile`, Header, redirect, and logout contracts behave exactly as before, with unmodified consumer code.
- `npm run lint` and `npm test` pass, evidenced by the verifier.
- `docs/auth-architecture.md` describes the implemented system with no stale invariant.
- No secret appears in tracked files, tests, logs, or artifacts.
